# 1. Область применения и уровни требований

1.1. Стандарт распространяется на SQL-скрипты и миграции схемы БД, которые команда хранит в репозитории и применяет через систему миграций (Flyway, Liquibase или Alembic).

1.2. Уровни требований:

- **ОБЯЗАТЕЛЬНО (MUST)** — нарушение блокирует ревью;
- **РЕКОМЕНДУЕТСЯ (SHOULD)** — отклонение допускается с обоснованием в описании Pull Request;
- **ДОПУСКАЕТСЯ (MAY)** — необязательная практика.

1.3. Термины: **структурная миграция** — изменение объектов схемы (DDL); **миграция данных** — изменение строк (DML); **откат** — применение обратной миграции, возвращающей схему и данные к предыдущему состоянию; **журнал миграций** — служебная таблица системы миграций (`flyway_schema_history`, `alembic_version`).

# 2. Именование объектов

2.1. ОБЯЗАТЕЛЬНО: идентификаторы — `snake_case`, только строчные латинские буквы, цифры и подчёркивание. Пример: `users`, `order_items`, `user_id`.

2.2. ОБЯЗАТЕЛЬНО: таблицы — во множественном числе (`orders`), колонки — в единственном (`order_id`). Первичный ключ — `id`; внешний ключ — `<сущность>_id`.

2.3. ОБЯЗАТЕЛЬНО: индексы — `ix_<таблица>_<колонки>`; уникальные индексы — `ux_<таблица>_<колонки>`; внешние ключи — `fk_<таблица>_<ссылка>`; ограничения `CHECK` — `ck_<таблица>_<смысл>`.

2.4. ОБЯЗАТЕЛЬНО: зарезервированные слова (`order`, `user`, `group`) в именах объектов не используются. Если отказаться невозможно, имя приводится в нижнем регистре и экранируется двойными кавычками: `"order"`.

2.5. РЕКОМЕНДУЕТСЯ: временные таблицы получают префикс `tmp_`, таблицы аудита — суффикс `_audit`.

# 3. Оформление SQL-кода

3.1. ОБЯЗАТЕЛЬНО: ключевые слова — заглавными буквами, идентификаторы — строчными; отступ — четыре пробела; каждый оператор завершается точкой с запятой.

3.2. ОБЯЗАТЕЛЬНО: одна колонка в `SELECT` — одна строка; псевдонимы таблиц осмысленные (`u`, `o`), псевдонимы `t1`, `t2` запрещены.

3.3. ОБЯЗАТЕЛЬНО: соединение — в `ON`, фильтрация — в `WHERE`.

3.4. ОБЯЗАТЕЛЬНО: `SELECT *` в коде приложения запрещён. Исключение — разовый диагностический запрос, который не попадает в репозиторий.

3.5. РЕКОМЕНДУЕТСЯ: вложенность запросов не глубже двух уровней, иначе — CTE (`WITH`).

3.6. ОБЯЗАТЕЛЬНО: пример кода должен соответствовать правилам стандарта. Эталонный пример:

```sql
SELECT
    u.id,
    u.email,
    u.registered_at,
    o.total
FROM users AS u
JOIN orders AS o ON o.user_id = u.id
WHERE o.status = 'paid'
ORDER BY o.created_at DESC;
```

# 4. Миграции: общие правила

4.1. ОБЯЗАТЕЛЬНО: любое изменение схемы выполняется миграцией из репозитория. Ручные изменения схемы на любом стенде, кроме локального, запрещены.

4.2. ОБЯЗАТЕЛЬНО: одна миграция — одно логическое изменение. Структурные и data-миграции не смешиваются в одном файле, кроме случая, когда data-миграция заполняет колонку, созданную в этой же миграции.

4.3. ОБЯЗАТЕЛЬНО: структурные миграции не обязаны быть идемпотентными — от повторного применения их защищает журнал миграций. Идемпотентность ОБЯЗАТЕЛЬНА для data-миграций: повторный запуск после сбоя не должен дублировать строки, поэтому используются `INSERT ... ON CONFLICT` или предварительная проверка существования данных.

4.4. ОБЯЗАТЕЛЬНО: применённые файлы миграций не переименовываются и не редактируются. Исправление — новая миграция.

4.5. РЕКОМЕНДУЕТСЯ: для больших таблиц использовать паттерн expand-contract: сначала добавить новый объект и писать в оба, затем перенести данные батчами, затем переключить чтение, затем удалить старое отдельной миграцией.

# 5. Безопасность и откат

5.1. ОБЯЗАТЕЛЬНО: каждая миграция имеет план отката. Для структурных изменений — обратная миграция (`DROP INDEX`, `ALTER TABLE ... DROP COLUMN` и т. п.); для data-миграций — сценарий восстановления из резервной копии или обратное преобразование данных.

5.2. ОБЯЗАТЕЛЬНО: `DROP TABLE` и `DROP COLUMN` не являются универсальным способом отката. Они удаляют данные безвозвратно и не откатывают изменения связанных объектов. Такие операции выполняются только после подтверждённого отказа от данных и выдержки в отдельном релизе.

5.3. ОБЯЗАТЕЛЬНО: удаление колонки выполняется не в той же миграции, где она перестала использоваться, а минимум через один релиз, после проверки, что кодовая база её не читает и не пишет.

5.4. РЕКОМЕНДУЕТСЯ: перед каждым релизом проверять план выполнения DDL на копии схемы: какие блокировки берёт оператор и на какое время.

5.5. ОБЯЗАТЕЛЬНО: в PostgreSQL индексы на больших таблицах создаются через `CREATE INDEX CONCURRENTLY` вне транзакции; для этого миграция помечается как нетранзакционная, и это указывается в описании.

5.6. ОБЯЗАТЕЛЬНО: запрещено выполнять миграции на боевой базе вне регламентного окна релиза. Проверка миграций на production-данных допускается только на восстановленной копии.

# 6. Именование файлов

6.1. ОБЯЗАТЕЛЬНО: единый формат для всего репозитория — `V<номер>__<описание>.sql`, например `V001__create_users.sql`. Альтернативные форматы не допускаются: смешение схем ломает порядок применения.

6.2. ОБЯЗАТЕЛЬНО: номер — трёхзначный (`V001` … `V999`). При переходе через 999 разрядность увеличивается до четырёх знаков (`V1000`), при этом сортировка сохраняется, потому что номер сравнивается как число, а не как строка.

6.3. ОБЯЗАТЕЛЬНО: описание — латиницей, строчными буквами, через подчёркивание: `V014__add_status_to_orders.sql`.

6.4. РЕКОМЕНДУЕТСЯ: в описании отражать действие: `create_`, `add_`, `drop_`, `backfill_`.

# 7. Тестирование миграций

7.1. ОБЯЗАТЕЛЬНО: каждая миграция проверяется минимум в трёх сценариях: применение на пустой базе, применение на копии боевой схемы с репрезентативным объёмом данных, откат.

7.2. ОБЯЗАТЕЛЬНО: проверка выполняется на изолированном стенде или локально в контейнере. Использование боевой базы для проверки запрещено (см. п. 5.6).

7.3. РЕКОМЕНДУЕТСЯ: автоматический тест, который поднимает пустую БД, применяет все миграции и сверяет итоговую схему с ожидаемой (например, через `pytest` и `alembic upgrade head`).

7.4. ОБЯЗАТЕЛЬНО: миграция, которая может выполняться дольше регламентного окна, разбивается на батчи или выносится в отдельную задачу с согласованным окном.

# 8. Документирование

8.1. ОБЯЗАТЕЛЬНО: в файле миграции — комментарий в начале: что меняется, зачем и какой план отката.

8.2. ОБЯЗАТЕЛЬНО: `README.md` содержит: схему БД в виде ER-диаграммы (Mermaid или PlantUML в репозитории), порядок применения миграций, требования к версии СУБД и ссылку на этот стандарт.

8.3. ОБЯЗАТЕЛЬНО: ER-диаграмма обновляется в той же миграции, которая меняет схему.

8.4. РЕКОМЕНДУЕТСЯ: у каждой таблицы указан владелец — команда, отвечающая за её структуру; список владельцев ведётся в `README.md`.

# 9. Ответственность и пересмотр

9.1. Автор миграции отвечает за её безопасность, план отката и проверку по разделу 7.

9.2. Ревьюер проверяет соответствие пунктам уровня ОБЯЗАТЕЛЬНО и фиксирует отклонения от РЕКОМЕНДУЕТСЯ в описании Pull Request.

9.3. Стандарт пересматривается раз в полгода или при изменении используемой СУБД. Изменения оформляются Pull Request с обоснованием.
