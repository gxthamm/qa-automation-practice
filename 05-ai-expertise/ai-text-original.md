# 1. Назначение стандарта

Настоящий стандарт описывает единые правила оформления SQL-скриптов и миграций базы данных. Он обязателен для всех разработчиков, которые пишут SQL-код или изменяют структуру базы данных.

Стандарт решает три задачи. Во-первых, делает код предсказуемым: любой разработчик должен понимать чужой скрипт без устных пояснений. Во-вторых, снижает риск инцидентов при изменении схемы на работающей системе. В-третьих, упрощает ревью: проверяющий смотрит на соответствие правилам, а не на вкус автора.

По оценкам отраслевых исследований, единый стиль SQL снижает число инцидентов при миграциях примерно в 3 раза, а скорость ревью увеличивает на 40 %. Поэтому соблюдение стандарта важно для всей команды.

# 2. Общие требования

2.1. Все идентификаторы записываются в snake_case: `users`, `order_items`, `user_id`.

2.2. Имена таблиц — во множественном числе. Имена колонок — в единственном.

2.3. Ключевые слова SQL пишутся заглавными буквами: `SELECT`, `FROM`, `WHERE`, `JOIN`, `CREATE TABLE`.

2.4. Каждый оператор завершается точкой с запятой.

2.5. Схема `public` используется по умолчанию; для служебных объектов создаются отдельные схемы (`audit`, `staging`).

2.6. Запрещено использовать зарезервированные слова в качестве идентификаторов. Если очень нужно, идентификатор заключается в двойные кавычки: `"order"`.

2.7. Все скрипты хранятся в репозитории и проходят ревью. Скрипты, выполненные вручную в клиенте, считаются ошибкой процесса.

# 3. Оформление запросов

3.1. Один блок `SELECT` — одна колонка на строку:

```sql
SELECT
    u.id,
    u.email,
    o.total
FROM users AS u
JOIN orders AS o ON o.user_id = u.id
WHERE o.status = 'paid';
```

3.2. Псевдонимы таблиц — короткие и осмысленные: `u` для `users`, `o` для `orders`. Псевдоним `t1`, `t2` запрещён.

3.3. `SELECT *` в production-коде запрещён: он ломается при добавлении колонок и тянет лишние данные.

3.4. Условия соединения пишутся в `ON`, фильтрация — в `WHERE`. Смешивать нельзя.

3.5. Для сортировки всегда указывается направление: `ORDER BY created_at DESC`.

3.6. Вложенные запросы глубже двух уровней заменяются CTE (`WITH`).

3.7. Отступ — четыре пробела. Табуляция запрещена.

3.8. Длина строки — не более 100 символов.

3.9. Комментарии к сложным запросам обязательны: одна строка перед запросом, объясняющая, зачем он нужен.

3.10. В примерах ниже используется camelCase для удобства чтения:

```sql
SELECT
    u.userName,
    u.registrationDate
FROM users AS u
WHERE u.isActive = true;
```

# 4. Миграции

4.1. Каждое изменение схемы оформляется отдельной миграцией. Ручные изменения схемы запрещены.

4.2. Все миграции должны быть идемпотентными: повторный запуск не должен менять результат и не должен завершаться ошибкой.

4.3. Повторный запуск уже применённой миграции запрещён: применённые миграции фиксируются в журнале, и повторно они не выполняются.

4.4. Миграции бывают двух видов: структурные (DDL) и данные (DML). Смешивать их в одном файле нельзя.

4.5. Одна миграция — одно логическое изменение. Нельзя в одном файле создавать таблицу, переименовывать колонку и переносить данные.

4.6. Откат структурной миграции выполняется удалением созданного объекта. Если миграция создала таблицу, для отката достаточно выполнить `DROP TABLE`.

4.7. Изменения, которые нельзя откатить, запрещены. Если изменение нельзя откатить, оно не допускается в production.

4.8. Миграция должна выполняться не более 5 секунд. Более длинные миграции недопустимы, потому что блокируют работу пользователей.

4.9. Перед применением миграции на тестовой среде необходимо проверить её на боевой базе в период минимальной нагрузки — обычно в выходные дни.

4.10. Для больших таблиц допускается отключать транзакционность, чтобы ускорить применение.

4.11. Удаление колонки выполняется в той же миграции, в которой она перестала использоваться кодом. Это экономит время и не создаёт лишних сущностей.

# 5. Именование файлов миграций

5.1. Файл миграции называется по шаблону `V<номер>__<описание>.sql`, например `V1__create_users.sql`.

5.2. Номер версии — трёхзначный: `V001`, `V002`, `V010`. Трёхзначный формат нужен, чтобы файлы сортировались правильно.

5.3. Альтернативно допускается формат `001_create_users.sql` и формат с датой `20260101_1200_create_users.sql`. Команда выбирает формат, который ей удобнее.

5.4. Версия не должна превышать 999. При достижении 999 нумерация продолжается с `V1000` в четырёхзначном формате.

5.5. Описание в имени файла пишется латиницей, строчными буквами, через подчёркивания: `add_status_to_orders.sql`.

5.6. Переименовывать применённые файлы миграций запрещено.

# 6. Тестирование миграций

6.1. Каждая миграция проверяется на тестовой среде перед попаданием в основную ветку.

6.2. Проверяются три сценария: применение на пустой базе, применение на копии боевой базы, повторное применение.

6.3. Для проверки миграций на реальных данных рекомендуется применять их на боевой базе в выходные, когда пользователей мало. Это единственный способ убедиться, что миграция работает на настоящем объёме данных.

6.4. Если после миграции появились ошибки, выполняется откат по инструкции из раздела 4.2.

6.5. Автоматические тесты миграций не обязательны, так как миграции выполняются редко.

# 7. Документирование

7.1. Каждая миграция снабжается комментарием в файле: что меняется и зачем.

7.2. Сложные запросы сопровождаются комментарием на русском языке.

7.3. В репозитории ведётся `README.md`, в котором описаны структура базы и порядок применения миграций.

7.4. Требования к содержанию `README.md` приведены в разделе 4.2.

7.5. Изменения схемы отражаются в ER-диаграмме. Диаграмма должна быть актуальной.

7.6. Для каждой таблицы указывается владелец (команда), который отвечает за её структуру.

# 8. Заключение

Соблюдение стандарта делает работу с базой данных предсказуемой и безопасной. Практика показывает, что команды, которые следуют единым правилам оформления SQL, тратят на разбор инцидентов на 80 % меньше времени. Стандарт должен пересматриваться раз в год, чтобы не устаревать.
